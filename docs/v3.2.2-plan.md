# Hentai Reader v3.2.2 Network Stability Plan

Status: implementation and automated verification completed; E-Hentai large-gallery
real-site acceptance pending.

## Scope

- Relicense the repository and generated userscript from MIT to GPL-3.0-only.
- Reduce E-Hentai/ExHentai rate-limit risk in large galleries without slowing
  direct-URL or local-materialization sites.
- Preserve foreground priority, bounded retry, shared image tasks and adapter
  isolation introduced in v3.2.1.

## Findings

- Reader byte prefetch previously used one global 10-ahead/4-behind window.
- The window bounds retained work, but does not itself cap byte-download
  concurrency. E-Hentai additionally resolves every image through a viewer HTML
  request, so a large window can create a sustained burst of viewer requests.
- E-Hentai viewer/page requests share a three-slot limiter. However, 429/503 was
  inspected after a limiter job had settled, leaving a short race in which the
  queue could start more work before the cooldown was armed.
- 4KHD resolves direct URLs and 18comic performs local anti-scramble
  materialization; neither should inherit E-Hentai's conservative viewer policy.
- Real viewer inspection confirmed E-Hentai returns a distinct Hath URL for
  `?nl=<token>`, but the shared fresh fallback could later revisit the original
  failed source and Reader could start one redundant full lifecycle afterward.

## Implementation

1. Add an optional generic `readerPrefetch` policy to site adapters.
2. Reduce the cross-site default to 6 ahead / 3 behind.
3. Set E-Hentai/ExHentai to 5 ahead / 2 behind while retaining viewer
   concurrency three and foreground promotion.
4. Detect E-Hentai 429/503 inside the limited task, arming cooldown before the
   request slot is released and the queue is pumped.
5. Keep retries serial and bounded; do not add request racing or site-name
   branches to Reader code.
6. Publish a generic `switching-source` lifecycle phase while an adapter resolves
   an alternate source, and show it in Reader as a loading-level HUD message.
7. Exercise the real E-Hentai adapter with local viewer fixtures: fail two Hath
   sources, follow two `nl` tokens, and publish the third source successfully.
8. Keep alternate tokens across transient resolver failures, skip already failed
   byte sources while tokens advance, and stop fresh fallback from returning to
   an old source after node switching.
9. Remove Reader's redundant second network lifecycle; the shared service now
   remains the sole owner of bounded resolve, source switching and byte retry.

## Acceptance

- Generated metadata, package metadata, README files and LICENSE agree on
  GPL-3.0-only.
- E-Hentai Reader retains at most eight items in its byte-prefetch window,
  including the current item; other sites retain the default ten.
- The first observed E-Hentai 429/503 pauses queued requests before a freed slot
  can start another queued job.
- Foreground navigation can still promote an existing shared task.
- Typecheck, unit tests and production build pass.

## Verification result

- TypeScript check passed.
- 55 unit, integration and architecture tests passed, including site-specific
  windowing, cooldown-before-queue-pump, visible source-switch state, and a full
  E-Hentai `node-a -> nl=node-b -> nl=node-c -> ready` chain. Additional
  regressions cover transient alternate resolution and refusal to revisit the
  original failed source.
- Production userscript built successfully at 316.46 kB (76.34 kB gzip), with
  `@version 3.2.2` and `@license GPL-3.0-only`.
